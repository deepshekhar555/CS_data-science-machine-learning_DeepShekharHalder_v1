Bike demand forecasting case study

This project models daily bike demand using a synthetic but realistic dataset designed to test honest forecasting. The key lesson is not merely to score well, but to avoid leakage, respect time order, and compare against a meaningful baseline before trusting any result.

Problem framing

  • Forecast daily bike demand for a fictional mobility service.
  • Use only data that would realistically be known before the day starts.
  • Respect chronological order in the train/validation/test split.
  • Report a naive baseline before any model tuning.
  • Keep the final test set untouched until the last step.
The main mistake in this type of project is leakage. Same-day temperature and rain appear in the dataset, but they are not available at prediction time and should not be used in a genuine forecast.

Insight

The meaningful result is not just that the candidate model has a lower MAE. It is that it improves over the strongest honest baseline while still obeying the real-world forecasting rule: only data available before the day starts may be used.

That is exactly the habit an experienced reviewer looks for in time-series work.
